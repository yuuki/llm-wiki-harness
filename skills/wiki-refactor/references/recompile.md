# 再編纂(recompile)の手順

`wiki-refactor` skill の従属資料。concept ページ 1 枚の受信箱(`## 未編纂の観察`、旧名 `## 横断的知見`)を主題節の命題へ畳み込み、読者が合成し直さずに現在の理解を得られる参照文書にする。規約の正本は `wiki/meta/conventions.md` §8(主題節の規則 1〜8、更新ルール 4・6)。この文書は手順と検査だけを定める。

subagent に委譲するときは、この文書のパスと対象ページのパスを渡す。subagent はこの文書と「0. 前提」の資料を読んでから着手する。

---

## 0. 前提

読む(順に):

1. `CLAUDE.md`(vault 全体の原則。日本語常体、コードスイッチング回避)
2. `wiki/CLAUDE.md`
3. `wiki/meta/conventions.md` — 特に §5(出典)、§7、§8、§13
4. `wiki/meta/token-discipline.md`
5. `wiki/meta/japanese-style.md`(keep / カタカナ / 漢語の方針)
6. この文書

読まない: `wiki/index.md`、`wiki/hot.md`、`wiki/log.md`、各 `_index.md`。カタログ更新は `scripts/wiki-catalog.py` の追記コマンドだけを使う。

例外: **再編纂は対象 concept ページ 1 枚を全文 `Read` してよい**。受信箱を主題節へ畳むには節全体を見る必要があり、excerpt の末尾 15 件では足りない。全文を読むのは対象ページだけで、姉妹ページは `wiki-excerpt.py --outline` で形だけ見る。

書き込みの前に `bash scripts/wiki-lock.sh acquire <path>`、書き終えたら `release <path>`。ロックは 60 秒で失効し、後から来た acquire に奪われる(`STALE_AFTER_SEC`。延長の手段は無い)。全文を読んで主題を設計しているあいだはロックを取らず、Edit / Write の直前に取り、書き終えたらすぐ離す。書き込みが 60 秒を超えそうなら、節ごとに書き込みを分けて都度取り直す。取る前に、読んだ時点からページが変わっていないこと(`git diff --stat -- <path>` や mtime)を確かめる。

1 回の再編纂 = 1 ページ = 1 コミット。複数ページをまとめない。ingest の途中で行わない。

実行環境の注意(過去の再編纂で実際に詰まった点):

- 実行シェルが fish のことがある。パス列を変数に入れて `git add` / `git commit` に渡すと単語分割されず失敗する。パスは直接列挙するか、`bash -c` / python で扱う。`echo ====` や macOS の `sed -i` も失敗しうるので、置換は python で行う。
- `wiki-catalog.py` と `recompile-finalize.sh` は内部でロックを取る。手動で `wiki-lock.sh acquire` したまま呼ぶと自分のロックを待って 60 秒でタイムアウトする。呼ぶ前に release する。
- 並行セッションの `git commit` や `git add` が、こちらの未コミット変更を巻き込むことがある。確定後は `git log --oneline -3 -- <page>` と `git status --short <page> wiki/log.md wiki/meta/claim-audit-YYYY-MM-DD.md` で、ページ・log・claim-audit 報告書が HEAD に入ったことを確かめる。入っていなければパス限定で自分でコミットする。履歴は改変しない。
- `prepend-log` には直前エントリの訂正手段がない。数え違いに気づいたら、そのエントリがまだコミット前で自分の書いたものである場合に限り、手動ロックのもとで `wiki/log.md` を直接直してよい。コミット済みのエントリは直さない。

## 1. 現状把握

対象ページの選定と着手宣言は再編纂キュー(`.vault-meta/recompile-queue.json`、git 追跡)を通す。キューは compile 負債の走査結果に、状態(pending / in_progress / done / rejected / blocked / skipped)と試行履歴、人間の却下理由を重ねたものである。

```bash
python3 scripts/recompile-queue.py refresh                  # 負債走査をキューへ同期(新規 pending、解消 done)
python3 scripts/recompile-queue.py next --limit 5           # 優先順の候補。rejection_reasons を必ず読む
python3 scripts/recompile-queue.py show "<page>"            # 対象ページの履歴と却下理由
python3 scripts/recompile-queue.py mark "<page>" --state in_progress
python3 scripts/wiki-excerpt.py "wiki/concepts/<page>.md" --outline
```

`rejection_reasons` が空でないページは、前回の再編纂が人間に却下されている。理由(例:「命題が観察の 1:1 言い換え」「出典を 2 件落とした」「節が 7 を超えた」)を作業メモの先頭に書き、同じ失敗を繰り返さない設計にしてから §2 へ進む。`blocked`(却下 3 回)のページは `next` に出ない。人間が `reopen` するまで着手しない。

そのうえで対象ページを全文読み、次を書き出す(作業メモ。ページには書かない)。基準は作業ツリーの版である。address の付与など、HEAD に無い frontmatter 行が作業ツリーにだけあることがある。`git show HEAD:` の行番号で受信箱を切り出すとずれ、その行を消してしまう。

- 受信箱の箇条書きを O1, O2, … と番号付けする。旧名 `## 横断的知見` の配下、`## 未編纂の観察` の配下、および `## 横断的知見（追記）` のような規約外の節の配下をすべて含める。新設時に置かれた空欄の案内文(「現時点では単一ソースのため、今後の ingest で追記する」の類。判定は `wiki_sections.py` の `is_placeholder_bullet`)は観察ではないので番号を振らず、再編纂後の受信箱からは消す。退避もしない。
- 受信箱の外に紛れた観察も拾う。観察として O 番号を振り、畳み込みと退避の対象にするのは次の 3 つの型である。
  - `## 未解決の問い` に置かれた出典付きの断定。後ろに「未解明である」「検証されていない」が続いていても、頭の太字や前の文が出典付きの事実を言い切っていれば断定である。出典を主語にして報告の動詞で言い切る文(「Gandalf([[@...]])は 1 日に複数回デプロイするクラスタが約 45% と報告する」)も、後ろに問いが続いていても断定である(`wiki_questions.py` の `question_assertions` はこの 3 つの型を数える)。「〜は未検証である」だけの項目は未解決点なので問い節に残す。
  - 主題節らしい見出し(例: 「プロセスの比較」)に ingest が積み増した箇条書き。
  - `## 定義` の 2 段落目以降に積まれた、太字で始まる出典付きの段落。ingest が定義節を第二の受信箱にした跡で、定義の本文(1 段落目)とは別に扱う。
- `## 定義` の中の `###` 小節・表・用語一覧も、命題か根拠に直す対象として書き出す。出典の無い用語一覧(「基本構成要素」の箇条書きなど)は、概念が何かを述べる定義の本文として残してよい。その場合も主張ごとに、このページがすでに引いている source で裏付けを探す。裏付けが取れない項目は、§3「出典の無い既存主題節の散文と表」と同じく、命題に起こさず `編纂前の定義小節` へ退避する。
- `# タイトル` の直下で `## 定義` より前に置かれた段落(以下、定義前の段落)も書き出す。`Navigation:` 行と案内の callout(`> [!important]` など)は対象外で、そのまま残す。定義前の段落は定義節の一部とみなし、中身で振り分ける。
  - 概念が何かを述べる段落は `## 定義` の 1 段落目へ寄せる。1 段落目と重なる文は落とし、足りない点だけを足す。
  - 出典付きの断定の段落は、定義節の 2 段落目以降に積まれた段落と同じく観察として O 番号を振る。
  - 用語一覧・表は定義節の `###` 小節と同じく、命題か根拠に直す。
  - どの場合も原文は `> [!note]- 編纂前の定義小節 YYYY-MM` に退避し(§4)、`## 定義` より前には何も残さない。
- 既存の主題節(あれば)とその命題。規約に合わない見出し(「知見」「観察」「考察」「示唆」「まとめ」「その他」「補足」「横断的」を含むもの)は改名または解体の対象。
- `## 定義` が 1 段落か、要約段落を既に持つか。
- `## 未解決の問い` のうち、受信箱の観察で既に答えが出ているもの。

## 2. 主題の設計

1. 観察 O1〜On を、**読者が検索語にできる名詞句**で 2〜7 個の主題に束ねる。出発点の雛形は 3 つ(歴史軸: 前史→転回→現在 / 問題構造軸: 問題→解決→限界 / 合意軸: 合意→論争→未解決)だが、雛形より**同じ domain の姉妹 concept の節構成に倣う**ことを優先する。姉妹は frontmatter `related` と `python3 scripts/wiki-resolve.py "<domain 語>" --type concept` で見つけ、1〜2 枚を `--outline` で見る。
2. 主題見出しに次の語を使わない: 知見 / 観察 / 考察 / 示唆 / まとめ / その他 / 補足 / 横断的。「設計上の含意」「実務への示唆」のような過程語も同類として避ける。
3. 1 節 10 命題を超えたら、7 節上限より分割を優先する。7 を超えたら親子化(conventions §13)の候補として報告に書き、それでも節は分ける。34 件を 1 節に押し込んで 7 に収めるのは失敗である。子ページの新設は本作業に含めない。
4. 既存の主題節があるページは、受信箱をその節へ畳むか、10 件超なら既存節を分ける。別の 7 傘に再梱包しない。次の場合は既存節を骨格に残したまま手を入れてよい。
   - 既存節の見出しが出典名(「Anatomy of an Incident が示す枠組み」「Spanner における実現方法」)や番号付きの章題なら、中身を表す主題の名詞に改名する(規則 1)。節の範囲は変えない。
   - 既存節のどれにも入らない観察が 3 件以上あり、共通の主題の名詞で束ねられるなら、新しい節を立てる。2 件以下なら受信箱に残すか、最も近い既存節の根拠に寄せる。
   - 畳むと 1〜2 命題にしかならない既存節は、隣の既存節と統合してよい。統合は再梱包ではない。
   - **統合した節の名前**は、統合後の命題を全部覆う主題の名詞に付け直す。旧見出しのどちらかを流用してよいのは、その語で統合後の命題をすべて言い表せるときだけである。2 つの旧見出しを「と」「・」でつないだだけの名前(「入力情報の 3 類型と前処理」)にしない。つないだ名前になるなら、統合するほど主題が近くないので統合をやめる。
   - **既存節の見出しが、畳み込んだ後の中身より狭くなったら改名してよい**(規則 1 は見出しが中身を表すことを求める)。畳んだ命題のうち旧見出しの語で言い表せないものが 2 件以上あれば改名する。1 件なら、その命題を最も近い別の節へ移すか受信箱に残す。改名は見出しを中身に合わせるだけで、節の範囲(どの命題がどの節に属するか)は変えない。例: ログベース異常検知の「入力情報の 3 類型」が時間間隔や表現の頑健性の命題を抱えたなら、「入力情報の類型と表現の頑健性」ではなく、両方を覆う「異常検知の入力表現」のような名詞に改める。改名した節も旧見出しごと `> [!note]- 編纂前の主題節 YYYY-MM` に退避し、log の `Renamed:` 行に「旧見出し → 新見出し」を書く(§7)。改名の前に `rg -F '[[<page>#<旧見出し>' wiki` で見出しへのリンクを確かめ、あれば報告に書く(他のページは直さない。§9)。
   - 手を入れた既存節の原文は `> [!note]- 編纂前の主題節 YYYY-MM` に退避する(§4)。
5. どの主題にも入らない観察は畳まず、`## 未編纂の観察` に残す(§4)。

## 3. 命題の執筆

主題節ごとに、観察を**命題**へ書き換える。

```markdown
## verifier の保証範囲

- **verifier が保証するのは単体安全性であり、共存配備・カーネル版差・プログラム所有メモリの競合は保証範囲外である。**
  - 根拠: [[@2024__SIGCOMM__NetEdit - An Orchestration Platform for eBPF Network Functions at Scale]] — 百万台規模の共存にはライフサイクル管理層が別途要る
  - 根拠: [[@2026__KubeCon Japan Community Day__XDPerf - A High-Performance Traffic Generator Built with WASM and eBPF]] — 6.1〜7.2 の multi-kernel CI が必要だった
  - 根拠: [[@2025__PhD__Scaling Telemetry Workloads in Cloud Applications - Chapter 3 Efficient TCP-UDP Socket-based Instrumentation in Kernel for Continuous Construction of Network Call Graphs]] §3.3.2 — マップ値の競合は verifier 対象外、3 層の同期で埋めた
```

規則:

- 命題行は太字の一文で「何が真か」を述べる。用語ラベル(「成功率」「SLE」)や見出しの再掲を命題にしない。対比(A と B を並べると X が見える)は根拠に降格させ、命題には書かない。命題の主語は対象世界の事物にする。「本 wiki の X 層が観測した…」「本 vault では…」のように wiki 自身を主語にしない(それは自己言及の変種)。
- 既存節に残っていた散文・番号付きリスト・用語解説は、命題形式に直すか根拠に降格する。主題節に再編纂前の地の文を残さない。
- 畳み込みは圧縮が原則。M(命題) が N(観察) 以上なら、複数観察を 1 命題の複数根拠へ寄せ直す。観察をほぼ 1:1 で命題化しただけなら未完了である。
- 根拠は `- 根拠: [[@source]] — 一行` の入れ子。反証・留保は同じ入れ子に `- 反証:` / `- 留保:`。姉妹 concept への横参照は `- 関連: [[concept]] — 一行` にし、`留保:` を横参照の置き場にしない。
- 根拠の説明は 1〜2 文に収める。数値・条件・図表番号は残し、背景説明や言い換えは削る。長くなるなら命題を分ける。
- 1 主題節の命題は 3〜8 件を目安にする。10 件を超える節は主題が 2 つ同居している(例: 「方針制御への拡張」と「verifier の保証範囲」)ので分ける。逆に 1〜2 件しかない節は隣の節へ寄せる。
- 見出しの和文と英字・数字の間には半角空白を入れる(「eBPF による」「成熟モデルの 2 軸」)。本文の表記と揃える。
- **畳んだ観察が引いていた出典は、命題の根拠にすべて引き継ぐ。** 1 つも落とさない(§5 で機械的に検査する)。
- **観察は出典の主張と同じとは限らない。** ingest 時の観察には、評価語の言い切り、数値の出所の取り違え、wiki 側の推論が混ざっている(過去の再編纂では観察の 1〜2 割に出典との食い違いがあった)。命題に起こす前に、次の 4 点を根拠行ごとに出典の抜粋と突き合わせる。
  - 評価語・程度語(「主因」「標準」「支配的」「最も」「過剰」)が出典の語と同じ強さか。出典が「一つの原因」「多い」「併用されることが多い」と述べているなら、その強さに合わせる。
  - 数値・年・名称が、その根拠行に引いた source の値か(別論文の値を借りていないか)。
  - 条件の脱落(「向上は保証されない」を「意味が無い」と言い切っていないか)と、一事例の一般化。
  - wiki 側の解釈(「〜と読める」「〜の先取りである」「〜の実本番での確認事例」)。出典に書かれていない推論は命題に起こさない。命題の `- 関連:` 行に降格するか、`- 留保:` に「wiki 側の解釈」と明記して残す。どちらにも置けないなら、`編纂前の観察` への退避だけにして、調べる価値があれば問い節に 1 行足す。
- 観察 1 件が命題 1 件になるとは限らない。3 件の観察が 1 命題の 3 根拠になることも、1 件の観察が 2 命題に分かれることもある。
- 矛盾は `> [!contradiction]` callout のまま残す。散文に溶かして消さない。
- ページの自己言及(「既出」「本ページが集約してきた」「本頁に初めて追加する」「本ページ既出の…」)を書かない。比較の履歴は log が持つ。
- 日本語常体。英単語を和文に素のまま混ぜない(japanese-style.md)。略語・固有名詞・数式・コード・wikilink は原語のまま。
- 主題節の中で `###` を使ってよいが、`###` の配下にも同じ命題形式を使う。

**出典の無い既存主題節の散文と表**(例: アンサンブル学習の比較表、Rooflineモデルの「アテンションは帯域律速」)は、主張ごとに出典を探してから扱いを決める。

1. 散文は文ごと、表は行ごと(比較表なら「どの手法がどの条件で何に優れるか」の 1 行)に主張を書き出す。
2. 主張ごとに、このページがすでに引いている source(`sources:`、他の命題の根拠、受信箱の観察の出典)の中から裏付けを探す。探し方は claim-audit.md §2 の順序と同じで、source ページを `wiki-excerpt.py` で見て、足りなければ抽出テキストを `rg` で引く。このページが引いていない source を新たに探しには行かない(それは ingest の仕事である)。
3. 裏付けが見つかった主張は命題に起こし、見つけた source を根拠行に付ける。表は命題の根拠に降格し、行ごとに出典を付ける。出典の付かない行を主題節に残さない。
4. 裏付けが見つからない主張は命題に起こさない。原文の退避(`編纂前の主題節`)だけにして主題節から外す。調べる価値があれば `## 未解決の問い` に「〜は出典で確かめられていない」と 1 行足す。「一般に知られている」で出典を補わない(§9)。
5. 命題に起こした主張も検査 4 の対象である。判定は**旧節に書かれていた主張**(主語・数値・条件をそのまま)に対して、根拠に付けた source が支持するかで付ける。出典に合わせて主張を弱めたり条件を足したりしたなら、旧節の主張に対して `unsupported` か `not_in_source` を付け、`note` に「旧主題節の散文(出典なし)から起こした → 手当て: …」と書く。起こし直した後の命題に対して `supported` を付けない。問題率は再編纂前の本文がどれだけ出典から外れていたかを測る数字だからである(§6)。

`## 未解決の問い` は、受信箱の観察で答えが出た問いを落とし、再編纂で新たに見えた問いを足す。答えの出た問いの内容は該当する命題の根拠に移す。問い節に、すでに出典付きで答えが書いてある項目(命題形式)があれば主題節へ移し、問いリストから外す。既存の問い節に「本ページが蓄積する」「本ページが扱う」のような自己言及が残っていれば、畳み込みと同時に書き換える。検査 2 の対象は主題節だけでなく問い節も含む。

## 4. 受信箱と退避

1. 畳めなかった観察(単一ソースで裏取りが要る、主題が立たない)だけを `## 未編纂の観察` に残す。残す理由を各項目の末尾に `— 保留理由:` で一言書く。残す観察に自己言及(「本ページ既出」など)や過程語が入っていれば、その句だけ書き換えてよい。内容と出典は変えない。残す観察の数値・帰属が出典と食い違っていても、項目の原文は直さない(出典の突き合わせは畳むときに行う工程で、残す観察はまだ畳んでいない)。代わりに保留理由の末尾に「出典と食い違う: 観察は X、source は Y」と書き、次の再編纂が畳むときに正す。残す観察が 0 件なら、見出しの直後に折り畳み callout だけを置く。「保留した観察: 0件」のような状況報告の箇条書きは置かない(受信箱件数に数えられる)。
2. 畳んだ元の箇条書きは**原文のまま**、`## 未編纂の観察` の末尾に折り畳み callout として退避する。

```markdown
> [!note]- 編纂前の観察 2026-09
> - (O1 の原文)
> - (O2 の原文)
> …
```

定義節の `###` 小節・表・散文の用語一覧を解体したときは、原文を同じ callout の末尾か、別の `> [!note]- 編纂前の定義小節 YYYY-MM` に退避する。既存の主題節の散文・表・命題を書き直したとき(命題形式に直した、節を統合した、命題文を弱めた)は、元の節を見出しごと `> [!note]- 編纂前の主題節 YYYY-MM` に退避する。表は行頭に `> ` を付ければ callout 内に置ける。退避 callout の名前はこの 3 つ(観察・定義小節・主題節)に限る。

`> [!note]-` の `-` が折り畳みの印。callout 内の行頭は `> ` で始めるので、受信箱の件数(`^- `)には数えられない。この callout は次回の再編纂で削除してよい。

3. 旧名 `## 横断的知見` の見出しと、規約外の節見出し(`## 横断的知見（追記）` 等)を除去する。節の並びを次に揃える: `定義` → `子概念`(あれば) → 主題節 → `未解決の問い` → `未編纂の観察` → `関連` → `出典`。
4. **受信箱に問いの形の項目が混じっていたら、問い節へ移す。** 問いの形とは、問い(「〜か」)か未解決点(「〜は未検証である」)だけを述べる項目である(`wiki_questions.py` の判定で `is_question_like` が真、`is_stray_assertion` が偽)。原文は他の観察と同じく `編纂前の観察` に退避し、`## 未解決の問い` には問いの文として 1 項目足す(既存の問いと重なれば統合する)。移した項目は畳み込んだ観察ではないので **N に数えない**。受信箱に残した件数 J にも数えない。log の `Moved to questions:` 行に件数を書く(§7)。出典付きの断定と問いが 1 項目に同居しているなら分ける。断定の部分は観察として畳み(N に数える)、問いの部分だけを移す。
5. **退避する観察に `> [!contradiction]` が入れ子で付いていたら、callout を本文へ移す。** 移し先は、その観察を畳んだ命題の直下(命題の根拠の入れ子の後、次の命題の前)である。callout の見出しと本文は変えずに写す。見出しを変えると、下に書く `contradiction-index.py` の重複除去が効かない。観察を受信箱に残す場合は、callout も観察の下にそのまま残す。退避 callout の中の原文からは callout を消さない(原文を書き換えない)。`contradiction-index.py` は、同じページの本文に同じ見出しの矛盾 callout があれば退避 callout の中の写しを数えないので、二重計上にはならない。退避にしか残っていない矛盾は索引に残る(本文へ移し忘れた印である)。

---

## 5. 定義の要約段落と frontmatter

- 主題節が 3 つ以上あるページは、`## 定義` の 2 段落目に現在の理解の要約(合意していること・争点・分野の移動)を 3〜6 文で書く。主題節の命題を読めば復元できる内容に留め、新しい主張を持ち込まない。主題節が 2 つ以下なら書かない。
- frontmatter: `updated: YYYY-MM-DD` を更新し、`tags` に日付タグ `YYYY/MM/DD` を追加し、`recompiled: YYYY-MM-DD` を置く(再編纂だけが更新する項目)。`sources:` を本文の `[[@...]]` と同期する。同期の対象は退避 callout を除く本文(主題節・未解決の問い・未編纂の観察・関連・出典)に現れる source である。callout にしか残らない出典は、本文から落ちたこと自体が検査 1 の失敗なので、`sources:` で埋め合わせない。`@` の付かない source ページや、根拠に引いた博士論文・サーベイ・書籍のハブ entity も `sources:` に含める。本文に無い既存の `sources:` 項目は削らずに残し、報告に書く。`address` は変えない。

## 6. 検査(書き終えてから、主張の前に必ず実行する)

```bash
P="wiki/concepts/<page>.md"

# 1. 出典を 1 つも落としていないか(再編纂前の wikilink 集合 ⊆ 再編纂後の本文)
#    前後とも退避 callout(行頭 `>`)を除いた本文で数える。再編纂後の callout には原文のリンクが残るので、
#    含めて数えると主題節から出典が落ちても必ず通ってしまう。再編纂前の側も除くのは、2 回目以降の
#    再編纂で前回の callout(削除してよい)にしか無いリンクを lost に数えないためである。
#    リンク切れを正しい名前へ差し替えた場合は旧名が lost に出る。差し替え先が本文にあることを確かめ、
#    `RENAMED="旧名=>新名;..."` で申告すれば除外する(申告の無い lost は失敗)。
#    source 以外(entity・concept)のリンクも数える。本文から命題の根拠へ書き換えて人物・組織・システムの
#    リンクが消えたら、`## 関連` に戻す。リンク先が実在しない名前だけは lost のままでよい(報告に書く)。
python3 - "$P" <<'EOF'
import os, re, subprocess, sys
p = sys.argv[1]
def outside_callouts(text):
    return "\n".join(l for l in text.splitlines() if not l.lstrip().startswith(">"))
before = outside_callouts(subprocess.run(["git", "show", f"HEAD:{p}"], capture_output=True, text=True).stdout)
body = outside_callouts(open(p, encoding="utf-8").read())
link = re.compile(r"\[\[([^\]|#]+)")
renamed = dict(x.split("=>", 1) for x in os.environ.get("RENAMED", "").split(";") if "=>" in x)
after_links = set(link.findall(body))
self_name = os.path.basename(p)[:-3]   # 自己リンクの除去は失敗にしない
lost = sorted(n for n in set(link.findall(before)) - after_links
              if n != self_name and not (n in renamed and renamed[n] in after_links))
print("lost wikilinks (outside parked callouts):", len(lost))
for name in lost:
    print("  -", name)
sys.exit(1 if lost else 0)
EOF

# 2. 自己言及・汎用見出しが残っていないか。
#    退避 callout(行頭 `>`)の中は原文保存なのでヒットしてよい。`rg -v '^[0-9]+:>'` で除外した残りが 0 であること。
#    「本ページが集約」だけでなく「本ページが蓄積/記録/扱う」「本 wiki」「本 concept」も対象。問い節も含む。
#    見出しは 未編纂の観察 のヒットだけなら可。旧名 横断的知見 は 0。
rg -n '既出|本ページ|本頁|このページ|この頁|本 ?wiki|この ?wiki|本 ?concept|本概念|本 ?vault' "$P" | rg -v '^[0-9]+:>'
rg -n '^## .*(知見|観察|考察|示唆|まとめ|その他|補足|横断的)' "$P" | rg -v '未編纂の観察'

# 3. 形が規約どおりか
python3 scripts/wiki-excerpt.py "$P" --outline
python3 scripts/wiki-concept-stats.py --compile-debt --page "$P"   # 終了コード 0 なら負債解消、1 なら残っている
#    一覧を --limit で切って rg で探さない。負債ページが limit を超えると圏外に落ちて解消と誤判定し、
#    部分一致(「障害予測」が「メモリ障害予測」に当たる)でも誤判定する。

# 3b. 1 節 10 命題超が残っていないか。出たら節を分ける(7 節上限より優先)。
python3 scripts/wiki-excerpt.py "$P" --outline | python3 -c "
import sys, re
text = sys.stdin.read()
bad = []
for line in text.splitlines():
    m = re.search(r'^## (.+?)  \((\d+) 命題\)', line)
    if m and int(m.group(2)) > 10:
        bad.append(f"{m.group(1)}: {m.group(2)}")
print('oversized sections:', len(bad))
for item in bad:
    print('  -', item)
sys.exit(1 if bad else 0)
"
```

検査 1 が失敗したら、落ちた出典を該当命題の根拠へ戻す。検査 2 で自己言及が出たら書き直す。

```bash
# 4. 命題が出典に本当にあるか(自己検査)。全命題のパケットを出し、references/claim-audit.md §2 で判定する。
#    --per-page はページの命題数 M 以上にする(§7 の数え方で M を出す)。足りないと M を超えた分が黙って漏れる。
#    出力先は作業者ごとの一時ディレクトリにする。/tmp の固定名は並列の再編纂どうしで上書きし合う。
W="$(mktemp -d "${TMPDIR:-/tmp}/recompile.XXXXXX")"
python3 scripts/claim-audit.py sample --pages "$P" --per-page 500 > "$W/claim-sample.json" 2> "$W/claim-sample.err"
```

stdout だけを JSON として保存する。stderr(`WARN` 行)を同じファイルへ流すと JSON が壊れるので、`2>` で別ファイルに分け、`.err` を読んで件数を確かめる。

**ハブ entity にだけ依る観察は、判定の前に章別の source ページへ張り替える。** ハブ(thesis / survey / book の entity)は要約水準で、`status: hub` のままでは章内の記述を照合できない。観察を命題に畳む時点で、ハブに書かれた主張を章別 source ページ(`wiki-excerpt.py` と `.raw/**/*.txt` の `rg`)で裏取りし、根拠行にはその章別 source を付ける。ハブへのリンクは `## 関連` に残す。

命題を手当てで書き換えると `sample` の id が変わる。判定 JSON の `id` と `line` は、手当て前に取ったパケットのまま写す(再 `sample` した id 集合とは一致しなくてよい)。`claim` だけを手当て後の文にする。

`sample` は `@` の付かない source ページも出典として扱い、ハブ entity(entity_type が thesis / survey / book)は `status: hub` の証拠として出す。ハブは要約水準なので、ハブだけに依る命題は章別の source ページを根拠に足してから判定する。根拠行があるのに検証可能な出典が 1 つも無い命題(人物ページや concept だけを引く)は `unverifiable: true` で出るので、`source_missing` と判定し、出典を足すか命題を弱める。stderr の `WARN` 行に件数が出る。

検査 4 で `not_in_source` / `unsupported` が出た命題は、コミット前に命題を弱めるか `- 留保:` を足す(まだ同じコミットの中なので退避 callout の追加は不要)。判定は `$W/claim-verdicts.json` に書き、§7 の `recompile-finalize.sh --verdicts` に渡す。台帳への記録と stage はスクリプトが行う。判定 JSON の書き方は次のとおり。

- `verdict` は sample を取った時点の命題に対する判定(手当て前)を書く。観察から命題を新しく起こした場合は「手当て前の命題」が無いので、その命題の元になった観察の主張(主語・数値・条件)に対する判定を書く。観察の誤りを命題を書く時点で正したなら、正した点を `note` に書き、判定は観察の主張に対するもの(`not_in_source` / `unsupported`)にする。手当てで命題を直しても `supported` に書き換えない。問題率は ingest と再編纂の質を測る数字なので、手当て後の判定で上書きすると消える。
- **複数の観察を 1 命題に束ねた場合**は、命題に持ち込んだ部分(命題の主語・数値・条件になったもの)ごとに、それを出した観察の主張を出典に照らす。判定は束ねた観察のうち**最も悪いもの**を付ける。主な出所の観察だけに対して付けない。脇の観察にあった誤りを命題を書く時点で正しても、それは ingest が持ち込んだ誤りであり、問題率に数えるべきだからである。悪さの順は `unsupported` → `not_in_source` → `source_missing` → `unclear` → `supported` とする。`note` には束ねた観察の番号と、どの観察の何が出典と食い違ったかを書く(「O3・O7・O9 を束ねた。O7 の 32 GPU は出典では 64 GPU → 手当て: 64 に直した」)。根拠行にだけ残って命題には入らなかった細部の誤りは命題の判定に含めず、claim-audit.md §2 の最後の規則どおり `note` を `根拠行:` で始めて書く。
- 旧主題節の散文・表から起こした命題は、旧節の主張に対して判定する(§3「出典の無い既存主題節の散文と表」の 5)。
- `id` と `line` はパケットのまま写す。`claim` は手当て後の命題文にする(台帳の報告書で現行の文を引けるように)。
- `note` は「何が出典に無かったか → 手当て: 何をしたか」の一文にする。
- `not_in_source` / `unsupported` を手当てした命題は、§7 で `--resolve <id> "<手当て>"` を付ける(スクリプトが record のあと `claim-audit.py resolve` を打つ)。打たないと台帳の未解決件数に残り続ける。手当てを見送った命題は resolve しない。

ingest 時の観察には、出典に無い数値や帰属の取り違えが混じっている(畳んだ根拠行にそのまま残る)。パケットの `numbers` は命題行と根拠行の数値を source ページと `.raw` の抽出テキストに機械的に照らしたもので、`missing` に出た数値は claim-audit.md §2 の手順で抽出テキストを `rg` で引いて確かめ、食い違えばコミット前に直す。`raw_only` に出た数値は source ページが原文の一部しか要約していない印で、ページに無いことを理由に落とさない。帰属(誰が・どの手法が)と条件は機械照合されないので、根拠行ごとに抜粋と突き合わせる。直したあと `python3 scripts/claim-audit.py numbers --pages "$P"` が終了 0 になるか、残った `missing` がすべて換算・導出値として説明できることを確かめる。PDF は開かない。再編纂した本人が判定するので甘くなりやすい。命題の主語・数値・条件の 3 点を出典の抜粋と突き合わせ、抜粋に無い語が命題に入っていれば `not_in_source` にする。

## 7. 記録とコミット

log のエントリをファイルに書き、`scripts/recompile-finalize.sh` で確定する。スクリプトは次の順に処理する。

1. 台帳を更新する。log の先頭追記、claim-audit の `record` と `resolve`、キューの `mark --state done` を行う。ここで失敗したら止まる。
2. 索引を更新する(`wiki-retrieve-refresh.py --pages`)。失敗しても `WARN` を出して先へ進む。
3. 対象パスだけを列挙してコミットする。index.lock の競合は再試行する。

```bash
cat > "$W/log-entry.md" <<'EOF'
## [YYYY-MM-DD] recompile | <page>
- Page: [[<page>]]
- Folded: N 観察 → M 命題 / K 主題節(<節名 1>, <節名 2>, …)
- Kept in inbox: J(保留理由の要約)
- Moved to questions: 受信箱から問い節へ移した問いの形の項目の件数(無ければ 0)
- Renamed: 旧見出し → 新見出し(改名した既存節ごと。無ければ行ごと省く)
- Parked: `> [!note]- 編纂前の観察 YYYY-MM`(退避した件数。N に問い節へ移した件数を足したもの)
- Summary paragraph: rewritten | not needed(主題節 2 つ以下)
- Dropped questions: 未解決の問いから落とした件数と行き先
EOF

bash scripts/recompile-finalize.sh "<page>" --log "$W/log-entry.md" \
  --verdicts "$W/claim-verdicts.json" \
  --resolve <id> "<手当て>"   # 手当てした not_in_source / unsupported ごとに繰り返す
```

- §6 の検査 4 では判定 JSON を書くまでにとどめ、`record` と `resolve` を手で打たない。スクリプトが同じコミットに入れる。手当てを見送った命題には `--resolve` を付けない。
- 手順を自作しない。台帳の更新を索引の更新より後ろに置いて `set -e` で繋ぐと、並行セッションとのロック競合で索引の更新が落ちたとき、キューの `done` だけが飛ぶ。
- 出力を grep で絞るときは、`ERR|WARN|FAILED` を必ず残す。`WARN: wiki-retrieve-refresh failed` が出たら、表示された再実行コマンドを後で打つ。
- `--no-commit` を付けるのは、統合で `merge_kind` が `recompile-keep` のときだけである。keep の再編纂と drop の `git rm` とリンク張り替えを、呼び出し側で同じコミットに入れる(conventions §8 更新ルール 6 が認める「1 ページ 1 コミット」の唯一の例外)。それ以外の再編纂は 1 ページごとにスクリプトにコミットさせる。その場合も、stage するのは対象ページ・`wiki/log.md`・キュー・claim-audit 台帳・当日の報告書だけにする。vault には無関係な未コミット変更が常にあるので、`git add -A` は使わない。キューは `.gitignore` 配下なので `-f` が要る(`mode.json` と同じ扱い)。

**却下されたとき**: 人間が再編纂結果を差し戻したら、コミットを revert するかページを戻したうえで、理由を一文でキューに残す。理由は次の試行が §1 で読む。

```bash
python3 scripts/recompile-queue.py mark "<page>" --state rejected --by human --reason "命題が観察の 1:1 言い換えで圧縮になっていない"
```

3 回却下されたページは `blocked` になり、`next` から外れる。構造の問題(親子化が先、主題が立たない)なら `--state skipped --reason` で当面外す。

記録の数え方: 「N 観察」は受信箱(旧名・規約外の節を含む)と、§1 で拾った受信箱外の観察(問い節の命題形式の項目、主題節に積まれた箇条書き、定義節と定義前の段落の出典付き断定)から畳んだ箇条書きの総数である。受信箱外の分を含めたときは「55 観察(受信箱 43 + 問い節 12)」のように内訳を併記する。旧主題節の出典の無い散文・表から命題に起こした主張も N に含め、内訳に「旧主題節 k」と書く。裏付けが無く退避だけにした主張は N に含めず、`Parked:` 行に「編纂前の主題節(うち退避のみ j)」と書く。受信箱に残した件数、問い節へ移した件数、空欄の案内文(`- 現時点では単一ソースのため…`。`wiki-concept-stats.py` も数えない)は N に含めない。「M 命題」は再編纂後の主題節にある太字命題の総数(既存節に足した分も含む)。観察と命題は 1 対 1 ではない(複数観察が 1 命題の複数根拠になる、1 観察が 2 命題に分かれる)。M は暗算しない。log を書く直前に次を実行し、出力の整数をそのまま貼る。log は追記専用なので、数え違いを後から直せない。

```bash
python3 scripts/wiki-excerpt.py "$P" --outline | python3 -c "
import sys, re
print(sum(int(n) for n in re.findall(r'\((\d+) 命題\)', sys.stdin.read())))
"
```

## 8. 報告

呼び出し元へ返すもの(ファイルには書かない):

- 畳み込み比(N 観察 → M 命題 / K 主題節)と主題節名
- 受信箱に残した件数と理由
- 検査 1〜4 の結果(落ちた出典 0、自己言及 0、汎用見出し 0、compile 負債から消えたか、命題の再検証の内訳と手当て)
- 親子化候補として報告すべき事項(主題が 7 を超えそう、子ページが要りそう)
- 規約側に見つけた不備(手順どおりに進まなかった箇所)

## 9. やらないこと

- 他のページ(姉妹 concept、source、entity)を編集しない。子ページの新設もしない。
- `wiki/index.md`・`hot.md`・`log.md`・`_index.md` を `Read`/`Edit` しない。
- 出典のない主張を新たに生まない。「一般に知られている」で埋めない。
- `> [!contradiction]` を消さない、言い換えで矛盾を無くさない。
- 受信箱に残した観察を勝手に削除しない(空欄の案内文は観察ではないので消してよい。§1)。退避 callout の原文を書き換えない。
- 複数ページを 1 コミットにまとめない。
