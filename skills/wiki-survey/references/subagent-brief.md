# subagent ブリーフの雛形

`wiki-survey` skill の従属資料。精読 subagent と執筆 subagent へ渡すプロンプトの雛形を定める。

subagent はユーザーの設問も、これまでの探索も、vault の規約も知らない。渡していない前提はすべて訓練データで埋められる。雛形の項目を削らない。

**どちらの subagent にもファイルを書かせない**。抽出結果も執筆した章も、テキストとして返させ、メイン文脈が保存する。`scripts/wiki-lock.sh` の stale 判定は既定 60 秒であり、分単位かかる工程の間ロックを保てない。複数の書き手が同じファイルを触ると、ロックが機能しないまま上書きが起きる。

---

## 1. 精読 subagent(フェーズ 3)

母集団を主題別に 5〜8 クラスタへ分け、1 クラスタに 1 体を並列投入する。`subagent_type` は `explore`(思慮の程度は "very thorough")を既定とする。

### 雛形

```
あなたは Obsidian vault（作業ディレクトリ = vault ルート）の wiki レイヤーから、
サーベイ執筆のための素材を抽出する担当である。

## 担当クラスタ

主題: <クラスタの主題を一文で>

担当ページ(絶対パスで全件列挙。これ以外は読まない):
- wiki/sources/@YYYY__SOURCE__Title.md
- wiki/concepts/<概念>.md
  (以下同様)

## 抽出する項目

各ページについて次を抽出する。

1. 著者と所属、発表年、掲載媒体。
2. その文献の主張を 1 文で。
3. 機構(なぜそうなるのか)。実装上の設計判断とその動機。
4. 具体的な数値。**必ず評価条件を併記する**(データセット名、ゼロショットかファインチューニングか、
   コンテキスト長、比較対象、ベンチマークの版)。条件が書かれていない数値は「条件記載なし」と付す。
5. 評価に使ったデータの出自(本番テレメトリ / 公開ベンチマーク / 研究室構築 / 合成)。
6. 限界。とくに**著者自身が認めている制約**を優先して拾う。
7. 他の担当ページと矛盾する記述があれば、両者の該当箇所を並べて報告する。
8. ページ本文に埋め込まれている図表があれば、埋め込みパスと原本の図表番号
   (例: `![[_attachments/arxiv-XXXX/figNN-....png]]` と「図 3」)。

## 厳守事項

- **担当ページに書かれていないことは書かない**。推測、補完、一般知識による穴埋めを禁じる。
  項目が見つからなければ「記載なし」と明記する。「記載なし」は失敗ではなく、こちらが必要とする情報である。
- **wikilink は原文のまま返す**。`[[@2026__arXiv__...]]` の `@` を落とさない。表記を整えない。
- 各主張の末尾に出典を `(Source: [[ページ名]])` の形で付ける。どのページの記述か 1 対 1 で辿れるようにする。
- 日本語、常体で書く。
- **担当ページ以外を読まない。ファイルを書き込まない。** 抽出結果はテキストとして返す。
- 担当ページが 800 行を超える場合は、全文を読む前に
  `python3 scripts/wiki-excerpt.py <path> --tail 15 --budget-tokens 1800` で概要を取り、
  必要な節だけを `rg -n` で位置特定して読む。

## 出力

ページ単位に見出しを立て、上記 1〜8 を箇条書きで返す。要約して圧縮しない。
最後に「クラスタ内で複数ページを並べて初めて見えた観察」を 3〜5 点、各点に 2 件以上の出典を付けて挙げる。
```

### 注意

- 「記載なし」の指示を落とすと、subagent は訓練データで穴を埋める。これが本 skill で最も起きやすい事故である。
- クラスタは文献数で均等割りせず主題の境界で切る。境界をまたぐ文献は両クラスタに渡してよい。重複は矛盾検出に役立つ。
- 担当ページは絶対パスで全件列挙する。「関連するページを探して読め」と指示すると母集団が制御できなくなる。

## 2. 執筆 subagent(フェーズ 4、章数が多いときのみ)

原則としてメイン文脈が執筆する。章数が多くて分担するときは、全員へ同一の共通ブリーフを渡す。導入章、座標系の章、横断的知見の章、未解決の問いは分担しない。

`subagent_type` は `generalPurpose` を使う。`explore` は探索向けで、長文の執筆には向かない。いずれの型でもファイルは書かせず、Markdown をテキストで返させる。

### 共通ブリーフに必ず含める 5 項目

1. **ページ全体の骨格**。全章の見出しと各章の役割、その subagent の担当章がどこに位置するか。これが無いと章をまたぐ論理が繋がらない。
2. **座標系の定義**。フェーズ 2 で立てた軸をそのまま渡す。担当章がどの軸に対応するか。
3. **素材**。フェーズ 3 で得た該当クラスタの抽出結果。担当章で使えるソースの一覧。
4. **執筆規範**。
   - 日本語、常体。`wiki/meta/japanese-style.md` の用語ポリシー(既定はカタカナ、定着した漢語は漢語、略語と固有名詞と wikilink は原語)。
   - `japanese-tech-writing` skill を適用する。ダッシュ(em ダッシュ、2 倍ダッシュ)を地の文と見出しで使わない。日本語の並列に中黒を使わない。一文一行。「重要なのは〜である」型の予告を書かない。見出しを結論のセリフにしない。
   - 全主張の末尾に `(Source: [[...]])`。素材に無い主張と数値は書かない。
   - 数値は評価条件つきで引く。異なる評価設定の数値を同一の表に並べない。
   - **wikilink を改変しない**。素材に現れた形をそのまま使う。
   - 個人の著者名を主語にする文(「Lu らの実測では」等)は、著者名の直後に括弧書きで代表的な所属を置く。所属は素材(精読 subagent が返した著者・所属の抽出結果)にある情報だけを使い、無ければ所属を書かず名前だけで通す。論文名やシステム名を主語にする文には適用しない。
5. **書かない範囲**。他の subagent の担当章と、姉妹ページへ譲る範囲。重複を避けるための除外リストを明示する。

### 雛形

```
あなたは wiki/surveys/<タイトル>.md の第 N 章「<章題>」を執筆する担当である。

## ページ全体の骨格
<全章の見出しと役割。担当章の位置>

## 座標系
<フェーズ 2 で立てた軸。担当章が対応する軸>

## 担当章の役割
<この章が答える問い。想定行数>

## 素材
<該当クラスタの抽出結果を貼る>

## 執筆規範
<上記 4 項目をそのまま>

## 書かない範囲
- 第 M 章が扱うため、<主題>は書かない。
- 姉妹ページ [[...]] へ譲るため、<主題>は書かない。参照で済ませる。

## 出力
Markdown をテキストで返す。ファイルへ書き込まない。
章見出しから始め、他の章の見出しは出力しない。図表は挿入しない(別パスで扱う)。
```

### 統合後にメイン文脈で必ずやること

- 節番号の統一。subagent ごとに採番が揺れる。
- セリフ型の見出しの改称。分担すると必ず出る。既存ページでも十数件の改称が必要になった例がある。
- LLM 口調の除去。
- 章をまたぐ重複の吸収。隣接章が同じ主張を別角度で述べていたら片方へ寄せる。
- 用語の統一。同じ概念に別の訳語が当たっていないか。
- 全 wikilink の実在検証。
