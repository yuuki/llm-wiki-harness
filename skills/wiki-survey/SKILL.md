# wiki-survey: wiki 横断のサーベイテキスト編纂

`wiki/sources/` と `wiki/concepts/` に積み上がった知識を横断し、単一の長編ページとして編み直す。出力は `wiki/surveys/<タイトル>.md` の 1 枚だけである。

## 適用範囲

**判定は設問の形で行う。行数や文献本数で判定しない。** 行数は書き終わるまで分からず、文献本数はフェーズ 1 まで確定しない。出力の寸法を起動条件にすると、判定できないまま wiki-query との間を往復する。

起動するのは、設問が次のいずれかを求めているときである。

- 主題の**設計空間**を体系的に教えること(教科書の要求)。
- 文献母集団の**地図**を作ること(サーベイの要求)。
- 対象そのものの**像**を、規格と実装と実測と学術を突き合わせて作ること(文献横断調査の要求)。

いずれの場合も、設問は「網羅」「体系的」「横断」に相当する要求を含む。単一の問いへ答えを返せば済む設問、単一ソースの解説、2 つの対象の差分の説明は本 skill の対象ではない。`wiki/surveys/` には 84 行から 377 行の比較ページや詳解ページが 19 枚あり、これらは wiki-query が deep で書いた。1 回の統合で答えが出る設問に 7 フェーズを回すのは無駄である。

**「〜について関連文献を調査して」は両側に読める**。この言い方は NIC 光トランシーバーのページ(616 行)を生んだ一方で、`QoAアンチパターン-防ぎ方`(150 行)のような短い調査にも使われる。判別は主題の側で行う。**規格と実装と実測と学術のうち 2 系統以上を突き合わせる必要があるなら本 skill、1 系統の文献を読んで統合すれば答えが出るなら wiki-query** である。迷ったらユーザーに「長編として編纂するか、回答として返すか」を確認する。

結果としてどうなるかの目安は、400 行を超え、13 本から 145 本の source を横断し、全文献を配置する座標系を本文に持つ、である(`wiki/surveys/` の長編 11 枚の実測)。これは**書き終わった後の自己点検**に使う。起動条件ではない。

母集団の妥当性はフェーズ 1 のゲートで判断する。薄いときの行き先は `autoresearch` と `wiki-ingest-*` であって、wiki-query へ戻さない。戻すと往復になる。

## 実例の使い方

既存の完成ページが仕様である。ただし内容の仕様と文体の仕様は別のページが担う。

| 役割 | ページ | 行数 | 見るところ |
|---|---|---|---|
| 教科書型の構成 | `wiki/surveys/時系列基盤モデルの教科書.md` | 728 | 前史から設計空間、スケーリング、エージェント層、批判、外側までの流れ |
| サーベイ型の構成 | `wiki/surveys/時系列基盤モデルのクラウド運用応用サーベイ.md` | 653 | 4 軸の座標系を第 2 章に置き、以降を運用タスクで切る組み方 |
| 文献横断調査型の構成 | `wiki/surveys/NIC光トランシーバーのモニタリング.md` | 616 | 対象の像を先に置き、層別に分解して実測へ降りる流れ |
| 整文の正本 | `wiki/surveys/RDMAネットワークモニタリングの教科書.md` | 1781 | ダッシュ 0 件、単一句のタイトル、部構成 |
| 整文の正本 | `wiki/surveys/NIC光トランシーバーのモニタリング.md` | 616 | ダッシュ 0 件、中黒 0 件 |

構成の実例として挙げた時系列 2 本は `japanese-tech-writing` 規範の適用前に書かれており、ダッシュがそれぞれ 41 件と 52 件、タイトルに「主題 — 副題」の形が残っている。**構成は倣ってよいが、文体は倣ってはならない**。文体は RDMA ページと NIC ページに倣う。

## 着手前に読むもの

1. [`wiki/meta/conventions.md`](../../../wiki/meta/conventions.md) は frontmatter、命名、出典の規約である。標準形式と矛盾する箇所はこれが優先する。
2. [`wiki/meta/japanese-style.md`](../../../wiki/meta/japanese-style.md) は keep とカタカナ化と漢語化のポリシーおよび用語集である。
3. [`wiki/meta/token-discipline.md`](../../../wiki/meta/token-discipline.md) により、`index.md`、`_index.md`、`log.md`、`hot.md` の全文を読まない。
4. `japanese-tech-writing` skill が執筆規範である。本文の整文はこれに従う。
5. `wiki-query` skill が検索経路(`retrieve.py` から `wiki-excerpt.py`)の正本である。本 skill は同じ経路を使い、wiki-query が deep でも扱いきれない長編編纂を引き取る。

骨格は [`references/skeletons.md`](references/skeletons.md)、subagent へ渡すブリーフは [`references/subagent-brief.md`](references/subagent-brief.md)、図表転載は [`references/figures.md`](references/figures.md) が正本である。同じ規則を本ファイルへ書き写さない。

## 手順

7 つのフェーズを順に進める。フェーズ 4 の執筆とフェーズ 5 の図表転載を混ぜてはならない。章構成が動くと図番号が崩れる。

### フェーズ 0　設問の確定と姉妹ページの確認

- ユーザーの設問を**逐語で**保存する。frontmatter の `question` にそのまま入れる。言い換えると、後から「何に答えたページか」が失われる。
- 設問が設計空間、地図、対象の像のいずれを求めているかを見る(適用範囲の節)。単一の問いへの回答で済むなら wiki-query へ渡す。文献本数と行数でここを判定しない。
- 骨格の出発点を選ぶ。判断は [`references/skeletons.md`](references/skeletons.md) の §1 に従う。この段階で型を確定する必要はない。フェーズ 2 で座標系が決まると自然に定まる。
- **姉妹ページを先に探す**。

```bash
python3 scripts/retrieve.py "<主題>" --top 10          # questions ページも返る
ls wiki/surveys/                                    # ファイル名の一覧
```

`scripts/wiki-resolve.py --type any` は `wiki/entities` と `wiki/concepts` と `wiki/sources` しか見ないため、`wiki/surveys/` の完成ページを 1 件も返さない。姉妹探索に使ってはならない。

- 主題が部分的に重なるなら、分業をリード文で宣言し、重なる範囲は書かずに参照で済ませる。クラウド運用応用サーベイは設計空間を教科書ページへ譲り、「本ページでは繰り返さない」と明記した。
- 主題がほぼ同一なら、新規作成ではなく既存ページの改稿を提案する。

### フェーズ 1　文献母集団の確定

1. 設問そのものと、設問を分解した下位問い 3 本から 6 本で `retrieve.py` を複数回叩く。

```bash
python3 scripts/retrieve.py "<設問の逐語>" --top 10
python3 scripts/retrieve.py "<下位問い 1>" --top 10
```

`retrieve.py` は BM25 インデックスまたは chunks が無いと終了コード 10 で失敗する。その場合は wiki-query と同じフォールバックへ落ち、`wiki-resolve.py` と `rg` で母集団を作る。

2. 出力の `candidates` を和集合にする。ヒットした concept のうち最も射程の広いものを**起点 concept** とする。

3. 起点 concept の frontmatter は `wiki-excerpt.py` を通さず、YAML 部分を直接読む。`scripts/wiki-excerpt.py` は `sources` と `related` を各 8 件で打ち切るため(`LIST_CAPS`)、45 件の `sources` を持つ concept でも 8 件しか見えない。母集団の拡張を excerpt に頼ると、目安の件数に届かないまま合意してしまう。本文の要約が欲しいときだけ excerpt を使う。

```bash
awk '/^---$/{n++; next} n==1' wiki/concepts/<起点>.md      # frontmatter を全件
python3 scripts/wiki-excerpt.py wiki/concepts/<起点>.md --tail 15 --budget-tokens 1800
```

frontmatter の抽出を行数で打ち切ってはならない。`sources` が 45 件ある concept では frontmatter だけで 105 行あり、`head` を挟むと母集団が切れる。

4. **rerank の縮退に備える**。ollama が不達だと rerank が何もせず、BM25 順位がそのまま出る。この vault では繰り返し起きている。縮退したら BM25 を参考値にとどめ、用語密度で補完する。

```bash
rg -c "<主要用語>" wiki/sources/ wiki/concepts/ | sort -t: -k2 -rn | head -40
```

5. **ゲート**。既存の長編 11 枚の `sources` 件数は 13、14、18、21、22、30、40、41、44、59、145 である。**下限はこの実測の最小である 13 本**とする。これを下回るなら編纂を始めない。不足している主題を挙げてユーザーへ報告し、`autoresearch` または `wiki-ingest-*` で文献を足してから戻る。wiki-query へ差し戻さない。

13 本で成立するのは、主題が絞れていて 1 本あたりの情報量が多いときである(`ポストモーテムの教科書` は 13 本で 751 行)。主題が広いなら 30 本を超えないと座標系が立たない。
6. 母集団のリストを**ユーザーへ提示して合意を取る**。以降は subagent を並列投入する高コスト工程であり、母集団を誤ると全部が無駄になる。章割りはこの段階では出さない。座標系より先に章を固めると、フェーズ 2 の設計が後付けになる。

`wiki/index.md`、各 `_index.md`、`wiki/log.md`、`wiki/hot.md` の全文は読まない。発見は `retrieve.py` と `wiki-resolve.py`、本文は `wiki-excerpt.py` を経路とする。

### フェーズ 2　骨格の設計

長編ページの質は、章の並びではなく**座標系**で決まる。座標系とは、母集団の全文献を配置できる 2 軸から 5 軸の分類のことである。

- 起点 concept が既に軸を持っているなら、それを使う。`[[RDMAネットワーク監視]]` の「計装点 7 層」と「時間軸 4 系統」は、そのまま二次元座標として独立章で明示され、全システムがそこへ配置された。
- 軸が無いなら母集団から帰納して作る。クラウド運用応用サーベイは「運用タスク、モデル供給形態、データ出自、評価軸」の 4 軸を作り、第 2 章を軸の定義に充てた。
- **座標系を明示する章を必ず本文に置く**。読者が以降の章を座標として読めるようになる。これは型を問わず必須である。
- 座標系の章を置いた後、以降の章は軸そのものではなく、**主要な軸の値**または**設計対象**で切る。軸の本数と章の本数を一致させようとしない。クラウド運用応用サーベイは軸を 4 本立てたうえで第 3 章から第 6 章を運用タスク(予測、観測ネイティブ、異常検知、診断)で切り、組織別の配備状況と横断的発見を別章にした。時系列基盤モデルの教科書は第 0 章に前史、第 1 章に 6 次元タクソノミーを置き、以降を各論、評価、応用、批判、外側、未解決で切っている。
- 評価データが結論を左右する主題(予測、異常検知、ベンチマーク比較など)では、**データ出自の軸**(本番テレメトリ、公開データ、合成)を立てる。これが無いと「ベンチマーク上の順位」と「実運用の改善」を混同する。層構造やライフサイクルが主題(RDMA の計装点、ホストの PCIe から NVLink までの層)なら、この軸は不要である。
- 主題が層またはライフサイクルで自然に区切れるなら、章数に関わらず部構成(第 I 部から)を使ってよい。`LLM学習インフラ実運用の教科書` は 13 部を一次構造にしている。区切りが無いなら章の通し番号だけで足りる。

章ごとに想定行数を割り当てて総量を見積もる。目安は文献横断調査が 400 行から 700 行、サーベイが 600 行から 900 行、教科書が 700 行以上(主題が広ければ 2,000 行を超えてよい)である。

**軸の被覆を確認する**。立てた軸のどの値にも文献が 1 本以上あるか。値が空の軸は座標系として機能しないので、軸を粗くするか、その値を「wiki のソースからは確認できない」として未解決の問いへ送る。この確認はフェーズ 1 ではできない。軸はここで初めて存在する。

座標系と章割りが固まった時点で、ユーザーへ提示して合意を取る。

### フェーズ 3　クラスタ別の並列精読

母集団を主題別に 5 クラスタから 8 クラスタへ分ける。文献数で均等割りせず、主題の境界で切る。

- 各クラスタに Explore subagent を 1 体割り当て、並列投入する。ブリーフは [`references/subagent-brief.md`](references/subagent-brief.md) の雛形を使う。
- ブリーフには必ず「**担当ページに書かれていないことは推測せず『記載なし』と明記する**」を含める。これを落とすと subagent が訓練データで穴を埋め、出典に遡及できない主張が混入する。
- **subagent にファイルを書かせない**。精読の結果も執筆した章も、テキストとして返させる。本文の Write はフェーズ 4 でメイン文脈が 1 回行い、以降の編集もメイン文脈だけが行う。`scripts/wiki-lock.sh` の stale 判定は既定 60 秒であり、分単位かかる執筆の間ロックを保てない。複数の書き手が同じファイルを触ると、ロックが機能しないまま上書きが起きる。
- **導入章、座標系の章、横断的知見の章、未解決の問いはメイン文脈で書く**。全体を見ないと書けないため、分担すると章をまたぐ矛盾が残る。

### フェーズ 4　執筆と本文の保存

frontmatter、章構成、必須節、callout、表の書式は [`references/skeletons.md`](references/skeletons.md) が正本である。ここでは骨格資料に書けない執筆時の判断だけを述べる。

- **出典が無い文を書かない**。source ページに書かれていない数値と主張は書かない。wiki に無いことは「wiki のソースからは確認できない」と本文に明記し、未解決の問いへ送る。
- **数値は評価条件つきで引く**。ゼロショットかファインチューニングか、コンテキスト長、ベンチマークの版が変われば比較できない。異なる評価設定の数値を同一の表で並べない。
- **人物と組織は初出で所属を併記する。** とくに「(著者名)らの〇〇では」という引用表現では、著者名の直後に括弧書きで代表的な所属を置く(例: 「Lu ら(上海交通大学)の実測では」「Guardの著者ら(Amazon)は」)。所属は該当 source ページの著者一覧、または wiki 内の entity ページから取る。事後学習で埋めない。ソースが著者名だけを引用し所属を明記していない(他文献からの孫引きなど)場合は、`wiki-resolve.py` で著者名の entity ページを引けないか確認し、それでも見つからなければ所属を書かず名前だけで通す。存在しない所属を作らない。
- 論文名やシステム名(「MegaScaleは」「OSDI論文は」)を主語にする文には、この所属併記は適用しない。対象は個人の著者名を主語にする文だけである。
- 整文は `japanese-tech-writing` skill に従う。一文一行、常体。ダッシュ(em ダッシュ、2 倍ダッシュ)を本文と見出しとタイトルから全廃し、日本語の並列の中黒を読点へ替える(wikilink 内のファイル名は不可侵)。「重要なのは〜である」型の予告と、結論を言い切るセリフ型の見出しは、書き上げた後に検査して除去する。

執筆の最後に、本文をファイルへ保存する。以降のフェーズはファイルに対する操作なので、ここで保存しないと図表転載も検査も走らない。

```bash
bash scripts/allocate-address.sh                                   # address: c-NNNNNN
# 本文の全文をメモリ上に組み立て終えてから lock を取る
bash scripts/wiki-lock.sh acquire "wiki/surveys/<タイトル>.md"
# ただちに 1 回の Write で保存する
bash scripts/wiki-lock.sh release "wiki/surveys/<タイトル>.md"
```

**本文を組み立て終えるまで lock を取らない**。`scripts/wiki-lock.sh` の stale 判定は既定 60 秒なので、lock を取ってから執筆すると、書き終わる前に他のセッションが同じ path を取れる。

図表を別コミットにするなら、**ここで本文のコミットを切る**。フェーズ 5 の後では図表が同じファイルに入っており、分けられない。

### フェーズ 5　図表の転載

本文の保存後に、独立したパスとして実施する。仕様は [`references/figures.md`](references/figures.md) が正本であり、探索・選定・実見・書式・検査の手順はそちらに従う。

**候補の実探索は省略しない**。母集団の全 source ページについて `_attachments/` の有無と中身を機械的に洗い出してから、選定基準(本文の主張の証拠になるか)で判定する([`references/figures.md`](references/figures.md) §1)。既存ページに 0 点の実例があることは、探索を飛ばして「今回も 0 点」と決める理由にならない。0 点は**探索した結果として初めて言える結論**であり、既定の答えではない。実務上は次の手順を踏む。

1. 母集団の各 source ページ本文から `![[_attachments/...]]` の埋め込みを `rg` で洗い出し、対応する `_attachments/<slug>/` の全ファイルを `ls` で一覧する。
2. 本文の章ごとに、既に書いた主張(とくに具体的な数値、比較、機構図)に対応する図がないかを、ファイル名とページ本文中のキャプション記述から当たりを付ける。
3. 当たりを付けた候補は**必ず実見**する(figures.md §3)。ファイル名と中身が一致しない例、複数の図が 1 ファイルにクロップされている例が実際に起きる。中身が主張を裏づけないもの、装飾目的のものは採らない。
4. 実見した結果、選定基準を満たす候補が 1 件もなければ、その旨(何ページの `_attachments` を何点確認し、なぜ不採用にしたか)を log に残したうえで 0 点にする。確認した件数が log から追える状態にする。

総括章・座標系の章・未解決の問いには貼らない(figures.md §2)。書籍ソース(`publish: false`)の図はユーザー判断を仰ぐ(figures.md §6)。

編集も lock 下で行う。転載は候補の実見と挿入を繰り返して分単位になるため、stale 時間を延ばす。

```bash
bash scripts/wiki-lock.sh acquire "wiki/surveys/<タイトル>.md" --stale-after-sec 1800
# 図表の挿入
bash scripts/wiki-lock.sh release "wiki/surveys/<タイトル>.md"
```

### フェーズ 6　検証

保存済みのファイルに対して以下をすべて実行する。修正が必要なら lock を取り直し、直してから release し、再度検査する。

```bash
bash scripts/wiki-lock.sh acquire "wiki/surveys/<タイトル>.md"   # 大きな直しは --stale-after-sec 1800
# 修正
bash scripts/wiki-lock.sh release "wiki/surveys/<タイトル>.md"
```

1. **wikilink の実在**。本文の `[[...]]` を全件抽出し、対応ファイルの存在を確認する。`![[...]]` の画像埋め込みは除外する。除外しないと `_attachments/` 配下の画像パスが wiki ページ名として抽出され、クラウド運用応用サーベイでは 32 件が混入する。source は `@` 付きでなければ `papers/` 側へ誤解決する(conventions §4)。

```bash
rg -o '(^|[^!])\[\[[^]]*\]\]' wiki/surveys/<タイトル>.md \
  | sed 's/.*\[\[//; s/\]\]$//; s/|.*//; s/#.*//; s/[[:space:]]*$//' \
  | sort -u \
  | while IFS= read -r n; do
      [ -z "$n" ] && continue
      [ -f "$n" ] && continue          # structures/000 Index.md のようなパス付き
      [ -f "$n.md" ] && continue
      base="${n##*/}"; base="${base%.md}"
      found=$(find wiki/sources wiki/concepts wiki/entities wiki/surveys wiki/questions structures \
                -name "$base.md" -print -quit 2>/dev/null)
      [ -z "$found" ] && echo "MISSING: $n"
    done
```

`.md` 付きのリンク(`[[structures/000 Index.md]]`)に `.md` を足すと必ず欠損になるため、パスとしての存在を先に試す。表示名(`|`)とアンカー(`#`)も落とす。

2. **数値の遡及**。本文の数値を 10 件ほど抜き取り、出典 source ページに同じ値があるか `rg` で確認する。
3. **画像パス**。転載した全パスの実ファイル存在を確認する([`references/figures.md`](references/figures.md) の検査手順)。欠損 0 件が条件である。
4. **整文の機械検査**。次を 0 件にする。

```bash
rg -o '—|―' wiki/surveys/<タイトル>.md | wc -l                        # ダッシュ
sed 's/\[\[[^]]*\]\]//g' wiki/surveys/<タイトル>.md | rg -o '・' | wc -l  # 中黒
rg -o '重要なのは|正面から|多角的|掘り下げ' wiki/surveys/<タイトル>.md | wc -l
```

中黒は wikilink を削ってから数える。`wiki/surveys/RDMAネットワークモニタリングの教科書.md` は素で数えると 14 件だが、その 13 件は `[[Mellanox・NVIDIA...]]` のようなファイル名の一部であり不可侵である。削らずに 0 件を目指すとリンクを壊す。

なお除去後に残る 1 件は、同ページのキャプションにある「層別・リンク別」という並列である。整文の正本として挙げたページにも取りこぼしはある。キャプションの並列は読点にする。

5. **重複**。隣接する章が同じ主張を角度を変えて繰り返していないか。姉妹ページと重なる記述が残っていないか。

### フェーズ 7　カタログ更新

ページ本体はフェーズ 4 とフェーズ 5 で保存済みである。検査を通してからカタログへ登録する。カタログは Read と Edit を使わず、スクリプトだけで更新する。

```bash
python3 scripts/wiki-catalog.py prepend-log --text "$(cat <<'EOF'
## [YYYY-MM-DD] wiki-survey | <タイトル>
- Question: 「<設問の逐語>」
- Output: [[wiki/surveys/<タイトル>]](address c-NNNNNN、N 行、M 章構成)
- Retrieval: retrieve.py の実行内容と rerank 縮退の有無、母集団の確定方法。
- 体制: subagent の分担とメイン文脈が書いた章。
- 骨格: 立てた座標系(軸)と、それを明示した章。
- 姉妹編との分担: 重複を避けた範囲と参照先。
- Key insight: 複数ソースを並べて初めて言えた観察。
- 執筆規範: japanese-tech-writing の適用結果(検査した項目と件数)。
- Gap: wiki のソースから確認できなかったこと。
EOF
)"

python3 scripts/wiki-catalog.py add-catalog-line \
  --file wiki/index.md --section "Surveys" \
  --line "- [[wiki/surveys/<タイトル>]]: 一行要約"

python3 scripts/wiki-catalog.py prepend-hot --text "## YYYY-MM-DD | wiki-survey | <タイトル>
- [[wiki/surveys/<タイトル>]]
- Focus: <このページが答えた設問>
- Key insight: <複数ソースを並べて初めて言えた観察>
"

python3 scripts/wiki-retrieve-refresh.py --pages "wiki/surveys/<タイトル>.md" --no-llm
```

`prepend-hot` の見出しは `## ` で始めなければならない。`scripts/wiki-catalog.py` の `split_hash_entries` は `^## ` だけをエントリ境界として扱うため、`### ` で書くとエントリとして数えられず、hot 窓の trimming(5 件、2000 トークン)から漏れて溜まり続ける。圧縮時に残るのは `Focus:` と `Key insight:` の行だけなので、この 2 行を必ず入れる。

`add-catalog-line` の重複判定は wikilink のターゲット文字列の一致で行う。既存の Surveys 節は `[[wiki/surveys/<タイトル>]]` の形なので、`[[<タイトル>]]` で書くと別物として二重登録される。

コミットは `wiki: add <タイトル>`。本文と図表を別パスで進めたなら、図表転載も独立したコミットとログエントリにする。ユーザーがコミットを止めている場合はこれに従う。

## やってはいけないこと

- **wiki に無い知識で穴を埋める**。訓練データから書いた主張は出典に遡及できず、ページ全体の信頼性を壊す。空白は空白として「未解決の問い」と log の Gap に記録する。
- 異なる評価設定の数値を同一の表に並べ、比較可能に見せること。
- `wiki/index.md`、`_index.md`、`wiki/log.md`、`wiki/hot.md` の全文読み込み。カタログを Read と Edit で更新すること。
- 既存の `papers/`、`research/`、`structures/`、`notes/` の書き換え。これらへは一方向参照だけを張る。MOC への逆リンク追記は人間の承認時のみ 1 件単位で行う。
- 実見していない画像の挿入と、パス未検証での保存。
- 本文完成前の図表挿入。
- **候補の実探索(フェーズ 5、figures.md §1)を行わずに図表転載を省略すること**。他ページに 0 点の実例があることは探索を飛ばす理由にならない。ユーザーから改めて図表挿入を求められてから探索を始めるのではなく、フェーズ 5 で自発的に行う。
- 姉妹ページと重複する章を書くこと。参照で済ませる。
- 書籍ソース(`publish: false`)の図を、ユーザー判断を仰がずに転載すること。publish 設定は変更しない。
- `.raw/` 配下の原本の改変。`wiki/log.md` の過去エントリの編集。
- 母集団が薄いまま編纂を始めること。文献を足す工程は `autoresearch` と `wiki-ingest-*` の仕事である。
