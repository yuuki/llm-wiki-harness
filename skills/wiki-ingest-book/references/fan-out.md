# 並列 fan-out の詳細と事例

`wiki-ingest-book` の従属資料。SKILL の「並列 fan-out」から移した逸話・失敗事例・長い説明である。規則の箇条書きは SKILL 側が正本である。

3 章以上は既定で **2 段階**(読み手 → 検査 → 書き手)の subagent 並行。**読み手と書き手は必ず別起動**する。プロトコルは汎用 `wiki-ingest` の「Batch Ingest › Parallel mode (subagents)」に従う。**1〜2 章は 1 体可**(断片 ingest。分離の固定費のほうが大きい)。

---

## 1. 読み手と書き手の分離と briefing の分割

3 章以上は 1 章につき **読み手 1 体と書き手 1 体**を別起動する。同一 subagent に「まず extract を書いてから、章本文を再読せずに書け」と 1 体で回してはならない。ターンをまたいで章本文が常駐文脈に残る。

1. **読み手(extract):** 自章テキスト(`chapters/ch-NN.txt`)を全部読む。[`extract-schema.md`](extract-schema.md) どおり `<scratch>/extracts/ch-NN.md` を書く。**見出しは空でも残す(schema)。** wiki ページは書かない。catalog / book entity 禁止。git 禁止。完了報告は extract パスと一行要約と図表点数だけ。
2. **検査:** 書き手起動前に `python3 scripts/wiki-extract-check.py --forbid-raw extracts/*.md` を 1 回かける。`MISSING` / `QUOTE-HEAVY` / `FORBID-RAW`・読み手失敗の章は書き手を起動せず、読み手をやり直す。
3. **書き手(write):** extract と [`subagent-brief.md`](subagent-brief.md) の書き手節と書き手用 briefing を読む。**章本文の全文 Read はしない。** locator の確認は grep のみ。ピンポイント Read は **1 章あたり最大 2 箇所、各 80 行**。超えるなら読み手やり直し。画像は書き手用 briefing の図表表 + コンタクトシート + extract の「図表」節。`wiki-page-write.py` で章 source を作り、entity / concept をヘルパーで書く。

**extract を `.raw` に置かない。** wiki にも置かない。git 管理しない。置き場は読み手用 briefing と同じスクラッチの `extracts/`(例: `/tmp/book-<slug>/extracts/ch-NN.md`)。

**briefing は読み手用と書き手用に分ける。** スクラッチに `briefing-extract.md` と `briefing-write.md` の 2 ファイルを書く。読み手の個別プロンプトは「まず `briefing-extract.md` を読む。`briefing-write.md` と brief の書き手節は読むな」+ 担当章の差分。書き手は「まず `briefing-write.md` を読む。章本文の原本は全文 Read するな」。1 ファイルにまとめるなら明確な 2 節にし、**読み手は書き手節を読むな**と書く。共通部分を 20 回書き写すと表記が揺れるので、書誌と訳語だけは両ファイルに同じ文面を置く。

**フル SKILL は渡さない。** 読み手には extract-schema と brief の読み手節。書き手には brief の書き手節。

オーケストレータが読み手に渡すもの: 書籍 slug と書誌 / 自章の原本パスとページ範囲 / extract 出力パス。`wiki-page-write` も本文テンプレも渡さない。

オーケストレータが書き手に渡すもの: extract パス / **全章の確定ページ名一覧**(Navigation 行用。原本パス列は置かない) / 自章の図表表 / frontmatter の共通値。**章本文の原本パスは briefing に書かない。** 必要なら「locator 確認は grep のみ。パスはオーケストレータが指定した 1 ファイルの該当行だけ」。書き手の個別プロンプトに章本文の全文を貼らない。

`briefing-extract.md` に入れるもの(これ以外は入れない):

- extract-schema の絶対パス
- extract の置き場(`<scratch>/extracts/`。**extract を `.raw` に置かない**)
- **git 操作の明示的な禁止条項**(下記)
- wiki 禁止(ページも catalog も book entity も書かない。`wiki-page-write` / `wiki-append` を呼ばない)
- 完了報告(extract パス・一行要約・図表点数)。「これから〜する」で終えない
- 書誌の最小(章題を間違えないための書名・slug)と本書固有の訳語
- **見出しは空でも残す(schema)**

`briefing-write.md` に入れるもの:

- 必読ファイル(`wiki/meta/conventions.md`・`wiki/meta/japanese-style.md`)の絶対パス
- 書誌情報一式(書名・原書・著者・訳者・出版社・発行日・ISBN・構成・slug)
- ヘルパーの呼び方(`wiki-page-write.py`・`wiki-append.py`。`allocate-address.sh` は直接実行しない。ヘルパーが落ちても新規を `Write` で作らない。止めて報告する)と frontmatter・本文テンプレートの完成形
- **バッチ固定の日付**(Step 0.3 で決めたもの)
- 本書固有の訳語
- 触ってはいけないファイルの一覧
- extract パス(自章)
- **全章の確定ページ名一覧の表**(章番号・ページ名。原本ファイル列は置かない)
- 既存 concept / entity の候補(`python3 scripts/wiki-resolve.py concept:"<語1>" concept:"<語2>" entity:"<名1>" --compact` で**全候補を 1 回で**確認し、`HIT` 行のパスを列挙)
- **git 操作の明示的な禁止条項**(下記)
- 短い章は 30〜50 行。該当のない節は省略可。推測で補完しない
- 完了報告(作成ページ一覧)。「これから〜する」で終えない
- ピンポイント Read の上限(1 章あたり最大 2 箇所、各 80 行。超えるなら読み手やり直し)

## 2. git 禁止を両方の briefing に書く

`briefing-extract.md` と `briefing-write.md` の両方に「`git add` / `git commit` / `git stash` / `git checkout` を実行してはならない。確認のための `git status` / `git diff` のみ許可する」と一節を立てる。**書かないと勝手にコミットされる**(実際に 1 体が fan-out の途中で自章分をコミットし、バッチが 2 コミットに割れた)。「commit はバッチ全体で最後に 1 回」とオーケストレータ側の手順に書いてあるだけでは subagent には届かない。

---

## 3. 章の中身の示唆は原本 grep で裏を取る

個別プロンプトに書く「章の中身の示唆」は、原本 grep で裏を取ってから書く。担当章に何が書かれているかを事前に示すと精度は上がるが、**裏を取らずに書いた示唆は誤りが混ざる**。実例(*A Philosophy of Software Design*、21 章)ではオーケストレータの示唆 3 件が原本に無かった — レッドフラグ 2 件の章帰属(巻末サマリの印字ページから逆算して外した。実際は別章)、テスト駆動開発への言及(別章の内容)、著者の姿勢に関する一文(Preface の記述)。いずれも subagent が原本照合で捕まえて書かなかったが、**捕まえられる保証はない**。書く前に 1 回 grep すれば全件確定できる:

```bash
# レッドフラグ・囲み記事の章帰属を全件確定する
grep -n "Red Flag" .raw/books/<slug>/chapters/*.txt | sed 's|.*/chapters/||'
# 特定の主張がどの章にあるか
grep -n "<主張の一部>" .raw/books/<slug>/chapters/*.txt
```

**巻末の「設計原則一覧」「用語集」等が示す印字ページから章を逆算しない**(オフセットの推定を誤ると隣の章に飛ぶ)。原本テキストを直接引くこと。

---

## 4. briefing は起動後に直しても届かない

`briefing-extract.md` と `briefing-write.md` は起動時に 1 回読まれるだけである。全員に効かせたいルールは投入前に書き切る。途中で気づいて追記したルールは、それ以降に投入する subagent にしか適用されない。読み手へ後から書き手用の禁止を足しても、既に起動した読み手には届かない。

---

## 5. Bash の作業ディレクトリ

Bash の作業ディレクトリはツール呼び出しをまたいで持続する。subagent が `cd .raw/books/<slug>/chapters` のような相対 `cd` を一度でも実行すると、以降の相対パスが全部ずれる。両方の briefing に「Bash では毎回 `cd <vault ルートの絶対パス> && ...` と明示してから相対パスを使う」と書いておく(オーケストレータ自身も同じ罠を踏む)。

---

## 6. 報告の照合

読み手の報告: extract パス / 一行要約 / 図表点数。wiki を書いたと言ってきたら誤りなので、その章の書き手は起動せず読み手をやり直す。

書き手の報告(10 行以内): **作成・更新したページを source 以外も含めて全て列挙**(entity・concept を「候補」として省略せず、実際に作成/更新したなら確定事項として書く。オーケストレータの事後判断に委ねるのは「作るべきか迷うもの」だけ)/ 章の一行要約(book entity の「構成と主要テーマ」に使う)/ key_claims / 気づいた矛盾。

**subagent の最終応答が完了報告になっていない場合がある**(例: 「Now update Fixstars entity...」のような次アクションの予告で応答が終わり、実際にはその編集が行われていないことがあった)。**オーケストレータは subagent の報告を鵜呑みにせず、fan-out 完了後に必ず `git status --porcelain=v1 -- wiki/ .raw/` で実際の新規(`??`)/変更(` M`)ファイルを確認し、報告内容と一致するか照合する。** 特に「更新した」と報告された entity/concept は `git diff -- <path>` で実際に今回分の差分が入っているか確認し、入っていなければ自分で追記する。「新規」か「更新」かの分類も、report の自己申告ではなく `git status` の `??`(新規)/`M`(既存)で判定し直す(例: 既存作成済み entity と誤認して「更新」と報告されるケースがあった)。

---

## 7. 触ってはいけないファイル

共有カタログ(`wiki/index.md`・各 `_index.md`・`hot.md`・`log.md`・`overview.md`・`.raw/.manifest.json`)と、**book entity ページ**。カタログは subagent が Read/Edit せず、fan-out 完了後に**オーケストレータだけが `wiki-catalog.py`**(prepend-log / prepend-hot / prepend-changelog / add-catalog-line / prepend-master)を呼ぶ。book entity は全章と接続するため、並列書き込みは lock があっても内容が衝突する。**オーケストレータだけが書く。**

entity / concept ページは subagent が作成・更新してよい(lock 必須)。ただし複数章で同じ著者・概念が出る場合に備え、オーケストレータは事後に名寄せ・重複チェックを行う。

---

## 8. ローリング 3〜4 体(ウェーブではない)

同時実行は **3〜4 体まで**(読み手と書き手を合わせる)。**ウェーブ(4 体投入 → 全員の完了を待つ → 次の 4 体)ではなくローリングで回す**。章の長さは大きくばらつき(2 ページの結び章と 24 ページの中心章が同居する)、ウェーブ方式だと毎回いちばん遅い 1 体に 3 体が待たされる。**読み手を先に回し、検査を通った章から書き手を投入する。** 1 体完了するたびに次を投入し、常に 3〜4 体が走っている状態を保つ。並行中に何が走っているかは毎ターン短く報告する。

**後の章の書き手ほど、先行章が触った concept を明示的に伝える。** ローリングで走らせると、同じ concept を扱う章が時間差で処理される。後発の書き手には「`wiki/concepts/トイル.md` は第2章・第3章の書き手が既に積み増している。必ず読んでから重複せず追記すること」のように、**具体的なファイル名と先行章**を伝える。lock は同時書き込みを防ぐだけで、内容の重複は防げない。読み手への申し送りは不要(wiki を書かない)。

**20 章超**でもローリングなら一括で流し切れるが、報告が溜まるので節目(部の切れ目など)で集約メモ化してコンテキストを節約する。**25 章超**は Part 単位で複数セッションに分ける選択肢をユーザーに提示する(book entity は初回セッションで骨格を作り、後続セッションは断片モードと同様に章リンクを追記する)。

log エントリはバッチ全体で 1 つ、commit も最後に 1 回。

---

## 9. 同じハブ concept は書き手を直列化する

同じハブ concept を奪い合う章は、**書き手**を並行させず投入順で直列化する。読み手は wiki を書かないので、同じ concept の章でも並行してよい。申し送りは重複を減らすだけでゼロにはできない。B ツリーを扱う 2・4・6 章、LSM を扱う 7 章のように**特定の concept が中心になる章が複数ある**なら、それらの書き手を同時に走らせず「2 章の書き手完了 → 4 章の書き手投入 → 完了 → 6 章投入」と順に流す。空いた枠には concept の重ならない章(別部の章など)の書き手や、未完了章の読み手を入れれば並行度は 3〜4 のまま保てる。この運用で、`B-Tree` への 5 章ぶんの積み増しが上書きも重複もなく層状に積み上がった(2 章が基礎、4 章が「理論と実装のギャップ」、6 章が「in-place 更新とラッチの 2 軸による亜種の系統化」、7 章が「LSM との増幅トレードオフ」)。**どの軸で書くべきかを書き手の個別プロンプトで指定する**とさらに効く。

## 10. 章検出の失敗事例

SKILL の Step 0 から移した逸話。規則の箇条書きは SKILL 側が正本である。

**少なすぎる(Part 単位への化け)。** 日本語書籍では outline の level 1 が「第Ⅰ部 SRE入門」のような部で、章は level 2 に並ぶことがある。この構成で level1-fallback が働くと、全 18 章が `chapters_count=13`(部+前付+付録+索引)のように化ける。実例(『SREをはじめよう』): level 1 が部・前付・付録、level 2 が「1章 はじめに」〜「18章 おわりに」。level 2 の開始ページから `--chapters "1=30,2=40,...,18=276,19=278,20=292,21=300,22=312"` を組み立てた(19〜21 は付録 A〜C、22 は索引以降を切り離すダミー章)。

**多すぎる(level 1 が章なのに節まで拾う)。** 実例(*A Philosophy of Software Design*): level 1 に `Preface` / `1 Introduction` 〜 `21 Conclusion` / `Index` が並んでいた。それでも `chapters_count` は 108 に化けていた(level 2 の節見出しまで拾われたため)。level 1 を並べて章がそこにあれば `--chapters` を組み立てるだけで済む。

**同じ level に部・章・節が同居する。** 実例(『詳説 データベース』): level 2 に「I.1 データベースの比較」(部の小節)・「1章 基本事項の紹介と概要」(章)・「1.1 DBMSアーキテクチャ」(節)がすべて並ぶ。level で絞ると全 14 章が 96 件に化ける。章題のパターンで絞ったあと、本編外は大きい番号へ割り当てた: `--chapters "17=25,1=31,2=49,3=69,4=87,5=105,6=139,7=157,15=195,18=197,8=201,9=225,10=235,11=245,12=275,13=291,14=315,16=351,19=355"`(17・18 = 各部序論、15・16 = 各部むすび、19 = 付録以降のダミー)。

**アウトライン 0 件。** 実例(*The Sciences of the Artificial* 3rd ed.): 目次が第 1 章を印字 p.1 と示し、PDF p.19 がその章扉だった。オフセット 18(印字ページ = PDF ページ − 18)が全巻で通用し、目次の印字ページ(1/25/51/85/111/139/169/183)を +18 して次を組み立てた(11 は索引以降のダミー、9・10 は序文)。

```bash
bash scripts/fetch-book.sh --force --chapters "9=11,10=13,1=19,2=43,3=69,4=103,5=129,6=157,7=187,8=201,11=235" "<pdf>" "<slug>"
```

序文も同じ捨て番号で切り出せる。同書では `9=11,10=13`(第 3 版序文・第 2 版序文)。

## 11. Step 0.3 の逸話

- `chapter_NN=` の題は節題に化ける。本セッションでも 2 章「Bツリーの基本」が「2.1 二分探索木」、4 章「Bツリーの実装」が「4.1 ページヘッダ」として返った。章題は `toc.txt` から拾う。
- 第 I 部と第 II 部に同題(「基本事項の紹介と概要」)が置かれる構成がある。担当 subagent に「あなたの担当は第 II 部の導入章」と書かないと、もう一方の章の内容を書きに行く。
- 20 章規模は日付をまたぐ。各 subagent に日付を判断させると `2026/08/12` と `2026/08/13` が混ざった。
- 骨格に書いた著者経歴はたいてい序文由来。実例では第 1 章担当が「指示された `contingency` は ch-01.txt に 1 度も現れない」と報告して誤りが発覚した。報告の「気づいた矛盾」を読み飛ばさない。
- 『詳説 データベース』は PDF p.197 = 印字 p.173。出典は印字ノンブルに統一しないと、subagent が矛盾として報告してくる。

## 12. 他セッション混在の分類(Step 4)

索引・log・manifest に同じページ一覧が何度も出てくる。人手で列挙し直すと必ず取りこぼす(実際に新規 entity 13 件のうち 1 件を落とし、後から `git status` と突き合わせて気づいた)。

`git status -- wiki/` には今回の ingest と無関係な変更が混ざる。別作業のリネームだけでなく、**別セッションが同じ vault で並行 ingest している**ことがある(実際、書籍の fan-out 中に別セッションが論文 3 本を ingest し、共有索引と多数の entity/concept を同時に触っていた)。

`--match` は git status に出た wiki 配下の新規・更新ページのうち**本文に書名を含むもの**だけを本書分とする。`--classify` は分類から漏れた差分を `CLASSIFY-OTHER` 行で列挙する。漏れた側を必ず目視する。

共有索引ファイルだけは自分の追記と他セッションの追記が同居しうる。`--classify` が `CATALOG` 行で各ファイルの追加行数を出すので、自分の追記行数と一致するかを見る(`--expect-catalog-lines N` を渡せば自動照合する)。一致しなければ扱いを判断してユーザーに報告する。fan-out に数時間かかる間に相手が先にコミットを済ませていることもあるので、`git log --oneline -5` で最新を取り直してから判断する。

## 13. 短い章・性質の違う章(書き手用)

分量の指示は **書き手用 briefing** に書く。読み手の extract は「短いから見出しを落とす」対象ではない。**見出しは空でも残す(schema)。**

極端に短い章・性質の違う章には、書き手へ分量の指示を添える。「おわりに」のような 2 ページの章に 60〜120 行のテンプレートをそのまま適用させると、出典に無い内容で埋める誘惑が生まれる。短い章には「30〜50 行で。該当内容がない節は省略してよい。推測で補完してはならない」と明記する。逆に多数の寄稿を集めた付録には「寄稿者ごとに逐語列挙せず、反復して現れる主題で束ねて出典付きで示す」と構成方針を与える。
